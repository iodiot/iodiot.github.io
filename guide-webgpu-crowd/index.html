01

One frame, five compute passes

The simulation step is a short GPU pipeline. Each pass prepares the data the next one needs, then the renderer reads the newest state.

clearGridReset cell counts
countAgentsHash agents to cells
scanCellsBuild cell offsets
scatterSort agent indices
steerUpdate every agent

Start with a clean grid

The clearGrid kernel resets the atomic count for every cell. This makes the data structure reusable each frame without rebuilding it on the CPU.

Count and record each agent’s cell

countAgents maps each position to a grid cell. An atomic increment gives that agent a unique slot inside the cell, stored in a compact per-agent buffer.

Turn counts into starting offsets

An exclusive prefix sum converts per-cell counts into ranges in one packed index array. A single 256-thread workgroup scans the current 80 × 80 grid.

Pack indices by cell

Each agent writes its index to cellStart[cell] + slot. The result is a contiguous list of neighbours for every cell, ready for local queries.

Read old state; write new state

steer computes neighbour forces and integrates motion into the other state buffer. The input and output buffers alternate each frame, so a thread never overwrites data another thread still needs to read.

Why one pass?

WebGPU inserts the required storage barriers between dispatches in the same compute pass. The CPU encodes the work but does not wait for individual agents or read their positions back.

02

Find nearby agents without checking everyone

Testing every pair would grow quadratically. A uniform spatial hash narrows each agent’s search to the cells around it.

Spatial hash

Turn positions into short lists

The world is split into 6,400 cells (80 × 80), each two world units wide. During counting, agents atomically reserve a slot in their cell; after the scan, the sorted index buffer makes each cell’s occupants contiguous.

// Count each agent into its cell
let c = cellIndex(cellCoord(agentsIn[i].xy));
let slot = atomicAdd(&cellCount[c], 1u);
agentCell[i] = vec2u(c, slot);

// Later, inspect the local 3 × 3 cells
for (var dy = -1; dy <= 1; dy++) {
  for (var dx = -1; dx <= 1; dx++) {
    inspect(cellCoord + vec2i(dx, dy));
  }
}

Bounded work

Neighbour iteration is capped at 32 agents per cell. This bounds the worst case when a large group collapses into one cell, while ordinary cells remain sparse.

03

Turn local rules into a moving crowd

Each agent applies classic boids behaviours to nearby neighbours, then adds a destination and obstacle avoidance.

01Separation

Steer away from nearby agents. The shader weights displacement more strongly at short distances to reduce collisions.

02Alignment

Blend toward the average heading of neighbours inside the radius so local groups move in a shared direction.

03Cohesion

Head toward the neighbours’ average position to keep a flock connected without forcing every agent into one point.

More than flocking

Destinations, obstacles and limits

Six moving streams of pedestrians have individual goals on a ring. Goal seeking pulls each agent toward its current destination; obstacle avoidance combines a look-ahead with a tangential force so traffic flows around obstacles. The shader then clamps acceleration and speed, integrates the position and enforces a hard non-penetration constraint.

Weights

Separation, alignment, cohesion, goal seeking and obstacle avoidance are live controls. Their balance changes the character of the crowd without changing the data pipeline.

04

Draw the crowd without copying its state

Simulation buffers stay GPU-resident. A vertex shader reads the current state directly for each rendered instance.

Ping-pong state

Two buffers, alternating roles

Every agent is stored as vec4(position.x, position.z, velocity.x, velocity.z). One buffer is read as the current state while the other receives the next state; their roles swap after a simulation step.

agentsA ──read──▶ compute ──write──▶ agentsB
   ▲                                  │
   └──────────── next frame ──────────┘

The renderer uses the same uniform buffer for shared parameters and obstacle placement. Agent geometry, positions and velocities are not uploaded as per-frame CPU arrays.

Instanced rendering

One pedestrian mesh, many agents

A procedural low-poly pedestrian mesh is drawn for every active instance. In the vertex shader, instance_index selects its agent state; velocity sets orientation, with a small lean and walking bob. The destination index supplies its colour.

  • 1 instanced draw
  • No instance vertex buffer
  • 4× MSAA
  • GPU timestamp query

The ground grid, obstacles and agents share one MSAA render pass. The camera orbits independently of the simulation.

05

Tune the workload and watch the GPU

Agent count changes dispatch size and instance count. The buffers are allocated for the maximum once, so changing the count does not reallocate them.

Dispatch sizing illustration

How many steering workgroups?

Each workgroup has 256 threads. The slider shows the number of workgroups needed for the steering kernel at a chosen active-agent count.

Measure, then adjust

What the live controls expose

  • Agent count from 1,000 to 100,000 and maximum speed.
  • Neighbour radius, constrained to fit within the two-unit cell size.
  • Separation, alignment, cohesion, goal seeking and obstacle avoidance weights.
  • Time scale, pause and re-seed controls.
  • FPS, frame time and GPU time where timestamp-query is supported.
Try it

Open the demo and compare the GPU-time readout as you raise the agent count. The bottleneck can shift: at high counts, vertex and raster work may cost more than the simulation itself.
